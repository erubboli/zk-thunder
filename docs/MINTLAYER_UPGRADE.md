# Mintlayer ZK Batch Settlement — Protocol Upgrade Spec

## Overview

This document specifies the changes required to `mintlayer-core` to support native ZK proof
verification for the ZKThunder L2 network. The goal is to allow ZKThunder to use Mintlayer as
its settlement layer: ZK proofs generated by ZKThunder are submitted as Mintlayer transactions
and verified by every full node during consensus, eliminating any trusted third party from the
settlement path.

This follows the same model Zcash uses for Groth16 proofs: no new opcodes or VM extensions
are required. Verification logic is implemented as a Rust function called from within the
existing transaction validation pipeline.

---

## Background: ZKThunder Proof System

ZKThunder is a fork of zkSync Era. Its prover pipeline produces a final **SNARK wrapper proof**
that is submitted to a settlement layer. There are two supported proof systems, both operating
over the **BN254 (Bn256) elliptic curve**:

| System | Crate | Notes |
|--------|-------|-------|
| **Fflonk** | `fflonk` (matter-labs) | Current default, protocol ≥ v29 |
| **Plonk** | `bellman` (matter-labs) | Legacy, protocol < v29 |

The final proof is represented as `L1BatchProofForL1` (defined in
`core/lib/prover_interface/src/outputs.rs` in the zkthunder repo):

```rust
pub struct FflonkL1BatchProofForL1 {
    pub aggregation_result_coords: [[u8; 32]; 4],   // 128 bytes of public inputs
    pub scheduler_proof: FflonkProof<Bn256, ZkSyncSnarkWrapperCircuitNoLookupCustomGate>,
    pub protocol_version: ProtocolSemanticVersion,
}

pub struct PlonkL1BatchProofForL1 {
    pub aggregation_result_coords: [[u8; 32]; 4],
    pub scheduler_proof: PlonkProof<Bn256, ZkSyncSnarkWrapperCircuit>,
    pub protocol_version: ProtocolSemanticVersion,
}
```

`aggregation_result_coords` are the four 32-byte public inputs that commit to the L2 batch:
state root, previous state root, L2-to-L1 log hash, and bootloader heap initial contents hash.

Proof sizes (CBOR-serialized):
- Fflonk: ~120–180 KB
- Plonk: ~30–50 KB

**Verification key (VK):** Each proof system uses a circuit-specific VK that encodes the
constraint system. The VK is deterministic for a given protocol version and must be hardcoded
as a consensus constant in Mintlayer. It changes only on ZKThunder protocol upgrades, which
are coordinated with a Mintlayer hard fork.

## New Output Type: `ZkBatchSettlement`

### Definition

Add the following variant to `TxOutput` in
`common/src/chain/transaction/output/mod.rs`:

```rust
/// Settle a ZKThunder L2 batch on Mintlayer. Non-spendable.
/// Contains a ZK proof attesting to the validity of the L2 state transition.
#[codec(index = 12)]
ZkBatchSettlement(ZkBatchSettlementData),
```

```rust
/// Data carried by a ZkBatchSettlement output.
#[derive(Debug, Clone, PartialEq, Eq, Encode, Decode, serde::Serialize, serde::Deserialize)]
pub struct ZkBatchSettlementData {
    /// ZKThunder L2 chain identifier.
    pub l2_chain_id: u64,
    /// Monotonically increasing batch number. Mintlayer enforces strict sequencing:
    /// each batch number must be exactly prev + 1 for the same l2_chain_id.
    pub batch_number: u64,
    /// State root of the L2 state after this batch (32 bytes).
    pub state_root: [u8; 32],
    /// Hash of all L2→L1 messages in this batch (32 bytes).
    pub l2_to_l1_log_hash: [u8; 32],
    /// Protocol version of the ZKThunder prover that generated this proof.
    /// Determines which VK is used for verification.
    pub protocol_version: u32,
    /// Proof system discriminant: 0 = Fflonk, 1 = Plonk.
    pub proof_type: u8,
    /// CBOR-serialized proof bytes (see serialization section).
    pub proof: Vec<u8>,
}
```

### Properties

- **Non-spendable**: Like `DataDeposit`, this output type cannot be used as a transaction input.
  It permanently records the settlement on-chain.
- **One per transaction**: A transaction may contain at most one `ZkBatchSettlement` output.
- **Ordering enforced**: The Mintlayer node tracks the latest settled batch number per
  `l2_chain_id` in its chain state. A `ZkBatchSettlement` is only valid if
  `batch_number == latest_settled + 1` for that chain.

---

## Serialization Format

The `proof` field is the CBOR encoding of `L1BatchProofForL1` as produced by the zkthunder
prover. No re-serialization is needed on the ZKThunder side: the bytes submitted to Mintlayer
are identical to those that would be submitted to an Ethereum verifier contract.

Implementations must handle both Fflonk and Plonk variants. The `proof_type` field is
redundant (the CBOR tag already encodes the variant) but is included for cheap early
rejection without full deserialization.

## Verification Logic

### Where to add it

Proof verification runs in `check_transaction()` in
`chainstate/tx-verifier/src/transaction_verifier/check_transaction.rs`, which is called for
every transaction in every block on every full node. This is the same function that validates
`DataDeposit` size limits and HTLC constraints.

### Algorithm

```rust
TxOutput::ZkBatchSettlement(data) => {
    // 1. Size guard — fail fast before any crypto
    let max_size = chain_config.zk_batch_settlement_max_proof_size(block_height);
    if data.proof.len() > max_size {
        return Err(CheckTransactionError::ZkProofTooLarge {
            actual: data.proof.len(),
            max: max_size,
        });
    }

    // 2. Retrieve the verification key for this protocol version
    let vk = chain_config
        .zk_vk_for_protocol_version(data.protocol_version, data.proof_type)
        .ok_or(CheckTransactionError::ZkUnknownProtocolVersion(data.protocol_version))?;

    // 3. Reconstruct the four public inputs from the settlement data
    let public_inputs = zk_verifier::build_public_inputs(
        data.state_root,
        data.l2_to_l1_log_hash,
    );

    // 4. Deserialize and verify the proof
    zk_verifier::verify(data.proof_type, &data.proof, &public_inputs, &vk)
        .map_err(|e| CheckTransactionError::ZkProofInvalid(e.to_string()))?;
}
```

### Batch sequencing check

Sequencing (batch_number == prev + 1) is a **stateful check** and must run in
`connect_transaction()` in
`chainstate/tx-verifier/src/transaction_verifier/mod.rs`, after proof validity is confirmed:

```rust
TxOutput::ZkBatchSettlement(data) => {
    let latest = self
        .chain_state
        .get_latest_settled_batch(data.l2_chain_id)?
        .unwrap_or(0);

    if data.batch_number != latest + 1 {
        return Err(ConnectTransactionError::ZkBatchSequenceError {
            l2_chain_id: data.l2_chain_id,
            expected: latest + 1,
            actual: data.batch_number,
        });
    }

    self.chain_state
        .set_latest_settled_batch(data.l2_chain_id, data.batch_number, data.state_root)?;
}
```

## New Crate: `zk-verifier`

Add a new internal crate `chainstate/zk-verifier/` with a single public function:

```rust
// chainstate/zk-verifier/src/lib.rs

pub enum ProofType { Fflonk = 0, Plonk = 1 }

pub struct VerificationKey { /* opaque */ }

/// Verify a ZKThunder SNARK proof.
///
/// - `proof_type`: discriminant for the proof system
/// - `proof_bytes`: CBOR-serialized L1BatchProofForL1
/// - `public_inputs`: reconstructed from ZkBatchSettlementData fields
/// - `vk`: the verification key for the declared protocol version
pub fn verify(
    proof_type: ProofType,
    proof_bytes: &[u8],
    public_inputs: &[[u8; 32]; 4],
    vk: &VerificationKey,
) -> Result<(), VerificationError> { ... }

pub fn build_public_inputs(
    state_root: [u8; 32],
    l2_to_l1_log_hash: [u8; 32],
) -> [[u8; 32]; 4] { ... }
```

### Dependencies

Add to `Cargo.toml`:

```toml
# Matter Labs fork — same repo used by zkthunder
fflonk = { git = "https://github.com/matter-labs/fflonk", tag = "<agreed tag>" }
bellman = { git = "https://github.com/matter-labs/bellman", tag = "<agreed tag>" }
```

These are `no_std`-compatible and have no network or filesystem access — safe for consensus code.

## Chain Config Changes

Add the following to `ChainConfig` in `common/src/chain/config/`:

```rust
/// Maximum size of the proof field in a ZkBatchSettlement output (bytes).
/// Default: 200_000 (200 KB — covers Fflonk with margin).
fn zk_batch_settlement_max_proof_size(&self, block_height: BlockHeight) -> usize;

/// Return the verification key for a given ZKThunder protocol version and proof type.
/// Returns None if the version is not recognized (causes tx rejection).
fn zk_vk_for_protocol_version(
    &self,
    protocol_version: u32,
    proof_type: u8,
) -> Option<&VerificationKey>;
```

VKs are embedded as binary constants compiled into the node binary. They must be updated
(via hard fork) whenever ZKThunder upgrades its proof system. The initial deployment includes:

| Protocol version | Proof type | Notes |
|------------------|-----------|-------|
| 29 | Fflonk (0) | First supported version |

## Protocol Upgrade / Activation

This change requires a **hard fork**: nodes running old software will reject blocks containing
`ZkBatchSettlement` outputs because the codec index `12` is unknown.

Activation mechanism:
1. Agree on an activation block height with the Mintlayer network.
2. Gate all new validation logic behind `block_height >= ACTIVATION_HEIGHT`.
3. Nodes on old software stop syncing at the activation block; they must upgrade.

Recommended: use the existing `ChainConfig` net upgrade mechanism already used for other
Mintlayer protocol changes.

## ZKThunder Integration

On the ZKThunder side, the `eth_sender` module's `PublishProofOnchain` path is replaced with
a `MintlayerSettler` that:

1. Receives an `L1BatchProofForL1` from the proof pipeline.
2. CBOR-serializes it.
3. Constructs a Mintlayer transaction with a `ZkBatchSettlement` output carrying the batch
   number, state root, l2_to_l1_log_hash, and serialized proof.
4. Signs and submits the transaction via the Mintlayer wallet RPC
   (`wallet_send_transaction` with a custom output).
5. Polls for the transaction to reach sufficient block depth (configurable confirmation
   threshold).

The `Commit` and `Execute` phases (which currently post to Ethereum) can either be retained
against Ethereum for data availability or replaced with `DataDeposit` transactions on
Mintlayer carrying the batch metadata. The DA worker's existing IPFS hash anchoring continues
unchanged.

## Security Considerations

**Proof uniqueness:** A valid proof for batch N can only appear once in the chain (enforced by
the sequencing check). Resubmitting a proof for an already-settled batch is rejected.

**VK lifecycle:** The VK is a consensus constant. A compromised or incorrect VK would allow
false proofs to pass. VK values must be derived deterministically from the ZKThunder circuit
source and verified by multiple independent parties before the hard fork.

**Proof system migration:** When ZKThunder upgrades its proof system (e.g., Fflonk v2),
a new protocol version number is assigned and a new Mintlayer hard fork activates the new VK.
Old VKs remain active for any un-settled batches from the previous version.

**Verification time:** Fflonk verification on a modern CPU takes approximately 100–500 ms.
This is incurred once per block that contains a `ZkBatchSettlement`. Block producers should
account for this in their block time budget. If ZKThunder produces one batch per minute and
Mintlayer has a block time above 60 seconds, at most one settlement per block is expected.

**Denial-of-service:** Invalid proofs fail fast (size check before crypto). The size limit
(200 KB default) bounds the work an attacker can force on a node with a malformed transaction.
Mempool policy should additionally require a fee floor proportional to proof size.

## Testing Requirements

1. **Unit tests in `zk-verifier` crate**: verify a known-good Fflonk proof passes; verify
   a bit-flipped proof fails; verify wrong public inputs fail.
2. **Integration tests in `chainstate/tx-verifier`**: a block containing a valid
   `ZkBatchSettlement` connects successfully; an invalid proof causes block rejection; a
   batch number gap causes block rejection; a duplicate batch number causes rejection.
3. **State persistence test**: after connecting several blocks with settlements, the latest
   settled batch is correctly read back from the database across node restarts.
4. **Chain reorg test**: rolling back a block containing a `ZkBatchSettlement` correctly
   decrements the latest settled batch counter.

## Open Questions for ZKThunder / Mintlayer Teams

1. **VK distribution**: How are VK bytes exchanged between the ZKThunder team and the
   Mintlayer network before the hard fork? Suggested: publish as a git-tagged file in the
   zkthunder repo with a SHA-256 checksum; Mintlayer core team independently verifies.

2. **Multiple L2 chains**: The spec supports multiple `l2_chain_id` values. Should the
   initial deployment restrict to a single ID, or support multiple from day one?

3. **Fee model**: Should the transaction fee for a `ZkBatchSettlement` be priced by proof
   size (like `DataDeposit`) or be a flat surcharge to cover verification computation?

4. **Proof system version negotiation**: If ZKThunder transitions from Fflonk to a new
   system, is there a grace period where both VKs are active simultaneously?
